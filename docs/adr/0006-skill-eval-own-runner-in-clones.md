# ADR-0006. Оцінка skills: власний раннер у клонах проєкту

- Статус: запропоновано
- Дата: 2026-10-09
- Приймає: автор проєкту

## Контекст

Фаза 3 (розділ 5.4 плану) вимагає команди `mezha skill eval`, яка робить дві речі:

- порівнює задачі зі skill-ом і без нього у свіжій сесії;
- міряє, чи завантажує Claude skill на промптах, де мав би, і чи не завантажує там, де не мав би.

Розділ 7 ставить ціль: precision тригера не менше 0.8. Definition of Done фази 3: оцінка показує різницю зі skill-ом і без нього на трьох реальних промптах.

План лишав вибір між обгорткою над skill-creator і власним раннером. Відтоді є ще й `claude plugin eval` (Claude Code 2.1.269 і новіші).

## Рішення

1. **Власний раннер на `claude -p`.** Він спільний з A/B з кроку 2c (модуль `bench`):
   - налаштування, sandbox і хуки самого проєкту, режим `acceptEdits`;
   - перевірки `check` у srt, `--unsandboxed-check` як явний вихід;
   - стеля вартості, яку mezha друкує й питає перед стартом.
2. **Файл кейсів** — `mezha/evals/<skill>.toml` або `--cases`.
   - `[[trigger]]`: `prompt` і `should_trigger`. Потрібні обидва види, інакше precision і recall нічого не кажуть.
   - `[[task]]`: `prompt`, а вердикт дають `check` (exit 0), `expect` і `reject` (регулярні вирази по фінальному повідомленню).
   - Тека `mezha/` захищена правилом `ask` і sandbox, тож агент не перепише кейси тихо.
   - Командні skills (`preset = "command"`) mezha відхиляє: Claude їх сам не завантажує, тож порівнювати нічого.
3. **Що оцінюється.** Skill береться з `mezha.toml` і файлу тіла в поточному стані, без `mezha compile`. Решта проєкту береться з бази: `origin/HEAD`, інакше `HEAD`, або `--base`.
4. **Варіанти.**
   - Тригери запускаються лише зі skill-ом і мають `trigger_turns` ходів (за замовчуванням 4). Сесія, якій забракло ходів, рахується.
   - Задачі запускаються зі skill-ом і без нього, з чергуванням порядку, як в A/B.
   - Без skill-а видалено каталог `.claude/skills/<skill>` і файл тіла.
   - В обох варіантах видалено файли кейсів, бо в них відповіді, і зроблено однаковий нейтральний коміт.
5. **«Завантажив»** означає успішний виклик інструмента Skill з цим іменем або успішне читання його `SKILL.md`. Перелік skills у події `init` для цього не годиться (перевірено на Claude Code 2.1.285):
   - skills з `user-invocable: false` там немає, а саме такі в mezha knowledge-skills за замовчуванням;
   - skill з `paths` зʼявляється в переліку (подія `commands_changed`) лише після того, як сесія торкнулася відповідного файлу.

   haiku іноді читає `SKILL.md` інструментом Read замість Skill, тому читання теж рахується.
6. **Кожен запуск іде в клоні репозиторію, а не в linked worktree.**
   - Перевірено на 2.1.285: у linked worktree Claude Code читає skills проєкту з основного checkout. Skill, видалений з worktree, лишається доступним, і варіант без skill-а насправді його має.
   - Памʼять агентів Claude Code читає з самого worktree, тож A/B лишається на worktree.
   - Клон (`git clone --shared`) бере обʼєкти з репозиторію, але remote у нього видалено, а власні коміти лишаються в ньому. Після запуску mezha видаляє клон і каталог, який Claude Code створює для нього в `~/.claude/projects`.
7. **Звіт.**
   - Precision і recall тригерів з ціллю 0.8 з розділу 7, а також таблиця задач, як в A/B, і скільки разів skill справді завантажився у варіанті з ним.
   - Рядки в `skill-evals.jsonl` містять лічильники, вартість і хеш промпта, без тексту.
   - `mezha metrics` показує останню оцінку кожного skill-а.
   - Повідомлення й diff задач лежать у `~/.mezha/metrics/<репозиторій>/skill-<skill>-<час>/`.
8. **Конфлікт імен зупиняє оцінку.** Якщо у варіанті без skill-а Claude все одно завантажив skill з цим іменем, то є skill користувача чи плагіна з тим самим іменем, і порівняння нічого не означає.

## Відхилені варіанти

- **Обгортка над `claude plugin eval`.**
  - Кожен запуск там іде в порожньому тимчасовому каталозі без CLAUDE.md, налаштувань, хуків та інших skills проєкту. Knowledge-skill проєкту без самого проєкту нема на чому перевіряти, а підготовку каталогу (`scaffold_script`) Claude Code виконує поза sandbox від імені людини.
  - Ціль — лише плагін, тож skill довелося б пакувати.
  - Звіт за замовчуванням публікується на claude.ai.
  - У JSON немає документованого переліку викликів інструментів по запусках, а precision і recall довелося б рахувати самим.
  - Ключ маніфесту `experimental.evals` документовано як такий, що ще може змінитися.
- **`run_eval.py` зі skill-creator.**
  - Скрипт пише тимчасовий файл у `.claude/commands/` самого проєкту і перевіряє лише опис, бо тіло там заглушка.
  - Тригером він вважає лише перший виклик інструмента.
  - Сесія йде просто в робочій теці проєкту.
- **Linked worktree, як в A/B.** Причина в пункті 6.
- **LLM-суддя для задач.** Він дорожчий і недетермінований, а `check` у srt і регулярні вирази поки достатні.

## Наслідки

- Оцінка показує поведінку в цьому проєкті з особистими налаштуваннями, skills і плагінами того, хто її запускає. Вони є в обох варіантах і конкурують за тригер, тож у колеги цифри можуть бути інші.
- Auto memory проєкту сесії оцінки не бачать: у кожного клону свій, порожній каталог. Це однаково для обох варіантів.
- `mezha.toml` в обох варіантах містить опис skill-а, а тіла у варіанті без skill-а немає.
- Малі вибірки шумні. Менше ніж за три повтори звіт не стверджує різниці, а precision на кількох промптах — орієнтир, не доказ.
- У Claude Code 2.1.285 є незадокументований `/plugin eval` для тригерів з полем `should_trigger`. Коли такий інструмент стане стабільним, `mezha skill eval` може стати адаптером над ним, як передбачає розділ 8 плану для dream.
