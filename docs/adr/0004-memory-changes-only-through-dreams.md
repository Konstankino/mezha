# ADR-0004. Памʼять агентів змінюється лише через dream

- Статус: запропоновано
- Дата: 2026-10-09
- Приймає: автор проєкту

## Контекст

Принцип 2 плану: кожен dream — це diff, який читає людина, і памʼять ніколи не змінюється мовчки.

Claude Code має власну памʼять субагентів: поле `memory` у frontmatter агента (`project`, `local` або `user`). Воно робить таке:

- завантажує в агента перші 200 рядків або 25 КБ `MEMORY.md` з `.claude/agent-memory/<name>/`, `.claude/agent-memory-local/<name>/` чи `~/.claude/agent-memory/<name>/`;
- додає агентові інструменти Read, Write й Edit та вказівки зберігати памʼять самостійно.

Крім того, Claude Code має вбудований дозвіл: будь-яка сесія може без запиту писати памʼять будь-якого агента в усіх трьох областях. Тож без додаткових правил агент переписував би свою памʼять посеред сесії, і ніхто б цього не переглядав.

## Рішення

1. `mezha compile` пише в `permissions.deny` правила `Edit(/.claude/agent-memory/**)`, `Edit(/.claude/agent-memory-local/**)` та `Edit(~/.claude/agent-memory/**)`. Claude Code перевіряє deny-правила раніше за свій вбудований дозвіл, тож у сесіях памʼять доступна лише для читання. Правило `Edit` покриває й інструмент Write.
2. Ті самі три шляхи додаються в `sandbox.filesystem.denyWrite`, щоб і команди в sandbox не могли туди писати.
3. Агентові з `memory`, якому spec не дає Write чи Edit, mezha додає ці інструменти в `disallowedTools`. Так `memory` не розширює права агента.
4. Тіло агента закінчується абзацом mezha. Він каже, що памʼять доступна лише для читання, а все варте збереження агент має виписати в розділі `## Lessons` у фінальному повідомленні. Цей розділ — сигнал для inbox кроку 2b.
5. Памʼять змінює лише `mezha dream` (крок 2b). Він працює в окремому git worktree без проєктних налаштувань і з guard-хуком, а результат стає комітом, який людина переглядає й пушить.
6. Для агента з `local`-памʼяттю `.claude/agent-memory-local/` має бути в `.gitignore`. Якщо це не так, `mezha verify` дає провал.

## Відхилені варіанти

- **Дозволити рідне самооновлення і переглядати git diff.** Зміни зʼявляються мовчки посеред сесії й легко потрапляють у коміт разом з іншими (`git add -A`). Окремого перегляду памʼяті немає. Крім того, `local`- і `user`-памʼять узагалі не видно в git.
- **Правило `ask` замість `deny`.** Діалог посеред сесії підштовхує натиснути «так», а в режимах без діалогів (`bypassPermissions`, `auto`) правило `ask` нічого не зупиняє.

## Наслідки

- Агент не може «запамʼятати» щось сам. Корисне він виписує в `## Lessons`, а потрапляє воно в памʼять після dream і перегляду.
- Людина також не редагує памʼять через Claude в сесії: deny діє для всіх. Файли памʼяті можна правити напряму.
- Sandbox-команди `git switch`, `rebase` чи `stash` через коміти, що змінюють памʼять, зупиняться на півдорозі: шлях закритий на запис. Такі команди виконує людина у своєму терміналі.
- Відоме обмеження: Claude Code дозволяє будь-якому агентові читати памʼять будь-якого іншого агента, зокрема `local`-памʼять PHI-агента. Крок 2b має це врахувати (inbox і dream для PHI).

## Крок 2b: як працює dream

Доповнено 2026-10-09.

1. **Запуск.** `mezha dream` запускає людина у своєму терміналі; всередині Claude Code команда відмовляє. Для кожної ролі з памʼяттю mezha збирає дайджести її запусків із транскриптів Claude Code: субагенти й сесії, запущені як `claude --agent <роль>`, у цьому проєкті та його worktree.
2. **Робоча тека — `~/.mezha/dreams/<репозиторій>/<час>/`**, а не `.claude/dream-inbox/` із розділу 3.6 плану. Причини:
   - sandbox не може туди писати (`denyWrite` на `~/.mezha`), тож паралельна сесія не підмінить дайджести чи worktree між перевіркою та читанням;
   - сесії не можуть її читати: це забороняє правило `Read(~/.mezha/dreams/**)`;
   - дайджести з PHI лишаються поза репозиторієм, і `.gitignore` для них не потрібен;
   - тимчасові теки macOS очищує, а цю — ні, тож після відмови є що прочитати.
3. **Dreamer** — окремий `claude -p --restricted` на кожну роль:
   - лише Read, Grep, Glob, Edit і Write;
   - без CLAUDE.md, без auto memory, без MCP-серверів і без файлів налаштувань, крім managed;
   - режим `dontAsk` з `--permission-prompts none` та єдине allow-правило: staged-копія памʼяті ролі. Копія лежить поза `.claude/`, бо в `--restricted` запис у файли конфігурації інструментів потребує людини.

   Дайджести надходять на stdin, а код проєкту dreamer читає у worktree. Якщо подія `system/init` показує інші інструменти, MCP-сервери чи інший режим, mezha зупиняє запуск. Поле `omitClaudeMd` не діє на агента головного потоку, тому CLAUDE.md вимикає змінна `CLAUDE_CODE_DISABLE_CLAUDE_MDS`.
4. **Перевіряє mezha, а не модель.** Після запуску mezha один раз читає staged-теку. Дозволено лише пласкі `*.md`, без `CHANGELOG.md` і символьних посилань, а worktree має лишитися без змін.
   - Жорсткі знахідки в доданих рядках скасовують dream: нічого не комітиться й не застосовується, а робоча тека лишається. Жорсткі знахідки — це приховані й керувальні символи, секрети, віддалені зображення та HTML, токени чат-шаблонів, а також PHI, якщо spec має PHI.
   - Фрази, схожі на інструкції, лише підсвічуються, бо справжні уроки теж їх цитують («уникай `--no-verify`»).
5. **Коміт із перевірених байтів.** Для project-памʼяті кожна роль дає один коміт на новій гілці `mezha/dream-<час>`.
   - mezha записує саме ті байти, які перевірив (`hash-object`, `update-index`), і звіряє дерево коміту.
   - Хуки репозиторію вимкнено для всіх викликів git під час dream (`core.hooksPath` вказує на порожню теку).
   - Пушить людина.
6. **Local- і user-памʼять** у PR не потрапляє. mezha показує diff і застосовує його лише після `y` у терміналі, попередньо перевіривши, що справжня тека не змінилася за час dream. Якщо stdin — не термінал, mezha лишає patch і нічого не застосовує.
7. **Курсор зберігається на машині**, у `~/.mezha/dreams/<репозиторій>/cursor.json`, бо різні клони мають різні транскрипти. Він зсувається після коміту, після застосування або після відповіді «no changes». У `CHANGELOG.md` ролі mezha пише лише факти й підсумок dreamer-а в огорожі коду.
8. **PHI.** Обмеження з розділу «Наслідки» враховано так:
   - кожна роль має окремий запуск і бачить лише свою staged-памʼять;
   - коли spec має PHI, дайджести всіх ролей очищуються за шаблонами PHI;
   - сесії не читають дайджести.

   Шаблони зменшують ризик, але не усувають його. Межа для PHI — local-scope.
9. **Відхилення від плану фази 2:**
   - у дайджестах немає вердиктів, escalations і auto memory, бо auto memory пишуть сесії без перегляду;
   - verify не перевіряє guard-хук, бо команду щоразу генерує сам бінарник, а її покривають тести.

   Guard-хук `dream-guard` лишається advisory.
