# ADR-0003. Межа для push: мережа, credentials і сервер

- Статус: запропоновано
- Дата: 2026-10-08 (доповнено того ж дня: крок 1b)
- Приймає: автор проєкту

## Контекст

Гейт `git push` з першого тижня читає текст команди, тому він advisory ([ADR-0002](0002-fail-closed-hook-command.md)). Щоб агент справді не міг запушити, потрібна межа, яку тримає ОС або сервер.

Push вдається лише тоді, коли одночасно є дві речі:

1. мережевий доступ із sandbox до хоста, що приймає запис (forge write endpoint): `github.com`, `api.github.com`, `uploads.github.com` тощо;
2. credential, який цей хост прийме.

Захист гілок на сервері — окремий шар. Він не зупиняє push, а обмежує, що push може зламати.

Що встановлено (документація Claude Code, вихідний код `@anthropic-ai/sandbox-runtime`, історія ocgen):

- Записи `deny` у `sandbox.credentials` з проєктного `.claude/settings.json` застосовуються. Claude Code обʼєднує `deny` з усіх рівнів налаштувань, і жоден рівень не може прибрати запис, доданий іншим. Ігноруються вони лише тоді, коли рівень проєкту вимкнено через `--setting-sources` (v2.1.246+). Записи `mask` із проєкту ігноруються.
- `sandbox.credentials` діє лише на команди в sandbox. Інструменти Read, Edit, WebFetch, MCP-сервери й хуки працюють поза sandbox.
- На macOS профіль Seatbelt у sandbox-runtime жорстко дозволяє `mach-lookup` до `com.apple.SecurityServer`, і жодне налаштування цього не прибирає. Отже, keychain доступний із sandbox. ocgen зафіксував це на практиці (коміт `1efb776`): `osxkeychain` віддав git токен, і нова гілка запушилась по HTTPS.
- На Linux і WSL2 Unix-сокети в sandbox заблоковані (seccomp), тож libsecret, gnome-keyring і helper `cache` недоступні; файли й змінні середовища ховаються через `sandbox.credentials`.
- Мережа з sandbox іде через проксі, що пропускає лише дозволені хости: `sandbox.network.allowedDomains` з усіх рівнів плюс хости з правил `WebFetch(domain:…)`.

## Рішення

1. `mezha compile` завжди генерує приховування credentials, без винятків у `mezha.toml`. Агент не робить fetch і push із приватних remote; це роблять люди.
   - `sandbox.credentials` з `deny` для відомих файлів і змінних середовища.
   - Такі самі правила `Read(...)` у `permissions.deny`, бо інструмент Read працює поза sandbox.
   - `env` для git: `GIT_CONFIG_COUNT=1`, `GIT_CONFIG_KEY_0=credential.helper`, `GIT_CONFIG_VALUE_0=""`, `GIT_TERMINAL_PROMPT=0`, `GIT_ASKPASS=""`.
2. Скидання credential helper-ів через `env` — **advisory**: команда може сама назвати helper (`git -c credential.helper=osxkeychain`). Воно закриває випадкове використання helper-а, зокрема у скриптах, яких матчер не бачить.
3. На macOS keychain сховати неможливо. Межа для push там одна: хости запису forge недоступні з sandbox.
4. mezha не пише в налаштування користувача чи managed. Сховища, які проєктний файл не може назвати (наприклад, перенесений `GH_CONFIG_DIR`), `mezha verify` позначає як провал із підказкою додати їх у налаштування користувача.
5. `mezha verify` виносить вердикт щодо push за таблицею:

   | Sandbox діє | Хости запису forge із sandbox | Credentials | Вердикт |
   |---|---|---|---|
   | ні (вимкнений, недоступний, `excludedCommands`, повтор без sandbox) | — | — | **провал** |
   | так | закриті | будь-які | **гаразд** |
   | так | відкриті або невідомо | досяжні | **провал** |
   | так | відкриті або невідомо | невідомо | **попередження** («не перевірено») |
   | так | відкриті | жодних відомих | **гаразд**, із переліком перевірених джерел |

   Захист гілок на сервері не помʼякшує провал: push гілки чи тегу однаково може запустити workflow із секретами.
6. За замовчуванням verify міркує статично: ефективні налаштування всіх рівнів, конфіг git, відомі властивості sandbox на кожній платформі. `mezha verify --probe` (крок 1b) запускає реальні перевірки в `srt`, якщо його встановлено.
7. Поки немає broker-а, `mezha approve` пропускає гейт, але push у sandbox однаково не проходить автентифікацію. Пушать люди. Broker перетворить approval на короткоживучий токен.

## Відхилені варіанти

- **git pre-push хук.** Обходиться через `git push --no-verify` або `git -c core.hooksPath=/dev/null push`, тобто це ще один advisory-шар.
- **Запис у налаштування користувача.** Не потрібен, бо `deny` з проєкту діють, а ще розширив би те, чого mezha торкається поза проєктом.
- **`git credential fill` як перевірка.** Може показати діалог keychain (а «Always Allow» назавжди розширює доступ), може стерти збережений credential після відмови сервера і заносить секрет у памʼять mezha.

## Наслідки

- Агент не може робити `git fetch` і `git pull` із приватних remote, викликати `gh` у sandbox і підписувати коміти (`~/.ssh` і `~/.gnupg` приховані). Ці дії виконує людина.
- `env` для git діє на весь процес Claude Code, а не лише на sandbox: оновлення plugin marketplace із приватних репозиторіїв може перестати працювати. Якщо в середовищі вже задано `GIT_CONFIG_COUNT` (devcontainer, CI), його записи перезапишуться; verify про це попереджає.
- На macOS додати `github.com` у `egress_allow` означає зламати межу, і verify покаже це як провал. Так само один клік «allow» для нового хоста посеред сесії зберігає його в налаштуваннях, і verify побачить це вже після факту.
- Припущення: Claude Code запускають із кореня проєкту, бо проєктні налаштування читаються лише зі стартового каталогу; версія Claude Code не нижча за 2.1.246.
- Файли, створені вже під час сесії (наприклад, `gh auth login` посеред сесії), можуть лишитися неприхованими до перезапуску.

## Крок 1b: захист гілок і `mezha verify --probe`

### Що показує проба

`mezha verify --probe` запускає перевірки без побічних ефектів у `srt` (`@anthropic-ai/sandbox-runtime` 0.0.79 або новіший). Налаштування для `srt` mezha виводить з ефективних рівнів:

- `network.allowedDomains`: дозволені хости разом із хостами правил `WebFetch(domain:…)`;
- `network.deniedDomains`;
- `filesystem.denyRead`;
- `credentials`: лише записи `deny`, обʼєднані з усіх рівнів;
- запис заборонено повністю (`allowWrite` і `denyWrite` порожні), бо проби нічого не пишуть.

Файл налаштувань лежить у приватному каталозі (0700, файл 0600) і зникає за будь-якого завершення, зокрема після тайм-ауту.

Дві частини:

1. **Мережа.** Для кожної пари (схема, хост, порт) з push URL, не більше пʼяти й не довше 60 с, виконується `git push --dry-run URL :mezha-probe-<nonce>`. Видалення ref, якого немає, падає ще до надсилання будь-чого, навіть без `--dry-run`. Помилка, що називає саме цей ref, зʼявляється лише після того, як сервер відкрив сесію push. git працює поза репозиторієм: зі scratch bare-репозиторію, без system і global конфігу, лише з протоколами https, http і ssh. Причина в тому, що `.git/config` агент може змінити (`insteadOf`, `http.proxy`, `ext::`, хуки) і так підробити результат.
2. **Credentials.** Перевіряється, які файли credentials читаються в sandbox (ключі ssh, `hosts.yml` gh, сховища git, `.netrc`, конфіги hub і glab, файл helper-а `store`, цілі симлінків) і які змінні з токенами там видно. Скрипт друкує лише індекси, не вміст.

Проба показує, що srt справді застосовує мережеві обмеження й приховує файли та змінні, **за тим прочитанням налаштувань, яке зробила mezha**. Вона не показує:

- keychain на macOS і credential helper-и: тут лишаються статичні висновки;
- як Claude Code сам обʼєднує налаштування: проба бачить прочитання mezha, а блок `env` з налаштувань у неї не потрапляє;
- SSH на macOS: усередині srt він падає завжди, навіть до дозволеного хоста, тож відмова там нічого не доводить;
- записи `mask`: srt їх не отримує, тому для таких credentials результат «невідомо».

Вердикт `push-boundary` з пробою:

- credential дійшов до сервера (сесія push, відмова в правах на запис, відхилений credential) — **провал** «показано в srt», з назвою хоста;
- хост, який проба застала відкритим, вважається відкритим, навіть якщо статичне прочитання каже інакше; закритим його робить лише відмова проксі srt (для SSH лише на Linux);
- коли проба й статичне прочитання розходяться, це **попередження**: помилка в прочитанні mezha;
- файли, прочитані в srt, і змінні, видимі в srt, стають доведено досяжними credentials;
- власний проксі sandbox (`httpProxyPort`, `socksProxyPort`) робить мережеву пробу невизначеною;
- таблиця з п. 5 не змінюється.

Рядки, що прийшли від сервера (`remote:`), не рахуються як локальні маркери: сервер не може підробити ні відмову проксі, ні сесію push. Без завершального маркера скрипта висновку немає.

`--probe` не поєднується з `--project-only`. Коли srt відсутній, застарілий, уже запущений довкола (`SANDBOX_RUNTIME`) або не може стартувати, verify завершується з кодом 2.

### Захист гілок

`branch-protection` питає GitHub через `gh` користувача, лише запитами (GraphQL і GET):

- GraphQL `refUpdateRule` показує лише класичний захист, `viewerPermission` показує права токена;
- REST `rules/branches/{b}` показує лише rulesets;
- `rulesets/{id}` показує `current_user_can_bypass` для кожного ruleset;
- `codeowners/errors` показує, чи є файл CODEOWNERS і чи він коректний.

Хост вважається GitHub-ом, лише якщо це `github.com`, ключ у `hosts.yml` gh або `GH_HOST`, бо URL береться з конфігу, який агент може змінити. gh запускається з тимчасового каталогу, завжди з `--hostname` і `-f`, без підказок, пейджера й кольору. Enterprise-токени отримує лише хост, який налаштував сам користувач.

| Результат | Умова | Статус |
|---|---|---|
| захищено | є блокування, яке ти не можеш обійти (ruleset `pull_request`, `update` чи `merge_queue` з обходом `never` або `pull_requests_only`; класичне правило з ≥ 1 схваленням, з code owners чи з `viewerCanPush: false` при праві WRITE і вище), **і** воно вимагає review code owners, **і** є коректний CODEOWNERS | **гаразд** |
| захищено без code owners | блокування є, але без вимоги code owners або без коректного CODEOWNERS | **попередження** |
| ти можеш обійти | кожне блокування ти обходиш (`always` чи `exempt`, або класичне правило, коли ти ADMIN) | **попередження**: агент із твоїм токеном запушить напряму |
| невідомо | gh відсутній, не залогінений чи впав; класичне правило з 0 схвалень без інших ознак; прихований ruleset | **попередження** |
| не захищено | немає ні класичного правила, ні блокування з ruleset | **провал**, якщо `push-boundary` провалено, інакше **попередження** |
| (додатково) | дозволено force push; доступ лише на читання; гілки за замовчуванням немає | **попередження** / пропуск / пропуск |

Захист гілок не помʼякшує провал `push-boundary` (п. 5): він обмежує, що може зламати push, а не те, чи push можливий.

### Лише довірені програми

verify не запускає `srt`, `gh`, `git`, `node`, `claude`, `bwrap`, `socat`, `bash` чи `mezha`, якщо вони лежать там, куди агент може писати:

- у проєкті;
- у `$TMPDIR`;
- у шляхах `sandbox.filesystem.allowWrite` і правил `Edit(...)`;
- у каталогах, куди можуть писати група чи всі, без sticky-біта.

Винятки для групи: групи, що й так мають root (`admin`, `wheel`, `sudo`), і приватна група користувача. Homebrew на macOS робить свої каталоги доступними на запис групі `admin`. Пропущені кандидати verify називає в деталях перевірки. `srt` отримує `PATH` без таких каталогів і без `NODE_OPTIONS` та `NODE_PATH`, бо його `#!/usr/bin/env node` шукає `node` у `PATH`. Це закриває і діру кроку 1a, де так само шукалися `git`, `claude`, `bwrap` і `mezha`.

### Відкладено до кроку 1c

- `--inside`, тобто перевірка зсередини сесії. Sentinel ненадійний, запит до невідомого хоста викликає в Claude Code діалог «allow», а статичні перевірки зсередини sandbox читають не те.
- Admin-ендпоінт захисту гілок (`enforce_admins`).
- Окрема обробка GHES.
- CI-завдання з srt: за розкладом, npm install за lockfile, `persist-credentials: false`.
