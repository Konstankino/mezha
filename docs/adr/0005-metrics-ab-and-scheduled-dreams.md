# ADR-0005. Метрики, A/B і dream за розкладом

- Статус: запропоновано
- Дата: 2026-10-09
- Приймає: автор проєкту

## Контекст

Фаза 2 (розділ 5 плану) вимагає трьох речей, крім ручного dream:

- dream за розкладом;
- метрик (розділи 3.7 і 7), що показують, чи окупається памʼять;
- A/B-раннера, який відпрацьовує 10 задач з памʼяттю і без неї.

План називав сховищем SQLite, а джерелом — зокрема `escalations.md`.

## Рішення

1. **Сховище — JSON Lines, а не SQLite.** Це файли `sessions.jsonl`, `dreams.jsonl` і `ab.jsonl` у `~/.mezha/metrics/<репозиторій>/`, по одному обʼєкту на рядок із `"v": 1`.
   - Чому не SQLite: даних мало (кілька рядків на сесію), а rusqlite компілює C для кожної цілі, тож перехресний clippy для windows-gnu і linux-musl потребував би mingw і musl.
   - Файли можна читати очима й шукати в них через grep.
   - Перезапис атомарний і йде під `flock`. Рядки, яких ця версія mezha не розуміє, зберігаються як є.
   - У сховищі лише лічильники, ідентифікатори, час, вартість і хеші, ніколи текст транскриптів.
2. **Вартість — це оцінка самого Claude Code** з рядків `cost-state`.
   - Продовжена чи відгалужена сесія копіює записи батьківської разом з її вартістю, і її власна сума починається з батьківської. Тому mezha бере лише записи з власним `sessionId` і віднімає успадковану вартість.
   - Сесія без `cost-state` (ще триває або впала) має невідому вартість і в середнє не входить.
   - Токени рахуються за останнім записом кожного `message.id`.
3. **Переробку вимірюють проксі,** і звіт так їх і називає.
   - Перше — подальші промпти людини в сесії.
   - Друге — повторні запуски того самого агента, але лише коли між ними був промпт людини; паралельні запуски не рахуються.
   - Це міра на сесію, а не на задачу, як у розділі 7.
4. **UNRESOLVED.**
   - Тіло кожного агента просить перелічити незроблене в розділі `## Unresolved`, з англійським заголовком за будь-якої мови відповіді.
   - Метрики рахують пункти останнього такого розділу по ISO-тижнях.
   - `escalations.md` з розділу 5.3 не потрібен: агенти mezha такого файлу не пишуть.
5. **Dream без правок.** `mezha dream` записує patch-id зміни памʼяті ролі (`git diff -U0` без `CHANGELOG.md`). Вирішує перший коміт базової гілки в історії first-parent, що змінив памʼять ролі:
   - той самий patch-id означає «злито без правок»: через merge-коміт, rebase на нову базу або squash;
   - штамп dream у повідомленні, але інша зміна означає «злито з правками».

   Вирішений результат більше не змінюється. Dream, гілки якого вже немає і який не злито, позначається як «dropped». Цей стан не зберігається, бо злиття, якого ще не видно до fetch, виглядає так само.
6. **A/B.** Кожна задача запускається як свій агент (`claude -p --agent`) двічі на кожен повтор, з чергуванням порядку:
   - у worktree бази з памʼяттю агентів;
   - у такому самому worktree з видаленим `.claude/agent-memory`.

   Умови однакові для обох варіантів:
   - **Worktree.** Обидва мають однаковий нейтральний коміт і нейтральні назви. Лежать вони в тимчасовій теці системи, бо в `~/.mezha` правила проєкту забороняють запис.
   - **Налаштування.** Сесії працюють з власними налаштуваннями, sandbox і хуками проєкту, у режимі `acceptEdits`.
   - **Auto memory.** Сесії її читають, але не пишуть: її ділять усі worktree репозиторію. Вимкнути її не можна, бо Claude Code вимикає разом з нею й памʼять агентів.
   - **Перевірка `check`.** Вона виконує код, який щойно написав агент, тому працює в srt з sandbox-налаштуваннями проєкту. `--unsandboxed-check` — явний вихід.
   - **Менше трьох повторів:** звіт не стверджує різниці.
7. **Розклад.** `mezha dream --schedule launchd|systemd|cron` лише друкує фрагмент, а встановлює його людина.
   - Фрагмент запускає `mezha dream --scheduled` напряму, без shell. Він відмовляє, якщо `mezha` лежить там, куди може писати агент.
   - Режим `--scheduled` працює лише з project-памʼяттю. Він пропускає роль, чий попередній dream ще чекає, і зупиняється, поки лишається worktree відхиленого dream.
   - Один dream проєкту за раз забезпечує `flock`, який ядро знімає, хоч би як завершився процес.
   - Windows Task Scheduler відкладено до фази 4.

## Відхилені варіанти

- **SQLite.** Причини в пункті 1.
- **Вимкнути auto memory в A/B** (`CLAUDE_CODE_DISABLE_AUTO_MEMORY` або `autoMemoryEnabled: false`). Перевірено на Claude Code 2.1.285: агент тоді не отримує своєї памʼяті, і варіанти нічим не відрізняються.
- **Нехай mezha сам встановлює розклад.** Це постійна зміна системи користувача, і помилку в ній легко не помітити. Надрукований фрагмент людина бачить перед встановленням.

## Наслідки

- Метрики показують тренди одного проєкту, а не доказ: проксі переробки грубі, вартість — оцінка.
- A/B порівнює памʼять з порожньою памʼяттю. Він не відповідає на питання з розділу 7, чи дорожчий mezha за Claude Code без нього більш ніж на 30%.
- Повернення з людського review поки не вимірюються, бо для цього потрібні дані PR (фаза 5).
- `mezha dream --scheduled` не торкається local- і user-памʼяті: такий dream запускає людина.
- Хто вимкне auto memory, той лишить агентів без памʼяті. verify про це попереджає.
