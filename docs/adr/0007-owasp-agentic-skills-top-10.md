# ADR-0007. Відповідність OWASP Agentic Skills Top 10

- Статус: запропоновано
- Дата: 2026-10-10
- Приймає: автор проєкту

## Контекст

У серпні 2026 OWASP випустив Agentic Skills Top 10: десять ризиків екосистем skills (AST01–AST10) і запобіжні заходи до кожного. Автор попросив привести mezha у відповідність до цього стандарту.

Більшість заходів стандарту адресовано реєстрам, видавцям skills і корпоративним інструментам: підписи видавців, transparency log, відкликання ключів, репутація, CMDB. mezha не є жодним із них. Це шар керування для одного проєкту:
- компілює agents, skills і rules з `mezha.toml`;
- доводить межу командою `verify`;
- пропускає памʼять лише через переглянуті dreams.

Тому кожен захід ми або виконуємо в межах цієї ролі, або свідомо відкладаємо з поясненням.

До цього кроку в mezha вже були заходи щодо ізоляції (sandbox), облікових даних, памʼяті агентів, безпечного розбору метаданих і змін під наглядом людини. Огляд знайшов такі прогалини:

- тіла skills, agents і rules ніхто не сканував;
- `` !`cmd` `` у skill виконувався під час завантаження;
- конфігурацію репозиторію, що запускає код (`.mcp.json`, `env`, `apiKeyHelper`), verify не перевіряв;
- особистий skill міг затінити проєктний;
- рішення гейта ніде не записувалися;
- auto memory і `CLAUDE.md` сесії писали без перегляду;
- вимогу підписаних комітів ніхто не перевіряв;
- `agent.tools` був необовʼязковим.

Повна мапа заходів: [`docs/owasp-ast10.md`](../owasp-ast10.md).

## Рішення

Кроки 4b–4h, по коміту на крок. Нових команд немає: усе входить у `compile`, `verify` і хуки (правило ADR-0001).

1. **4b. Тіла й метадані (AST01, AST04, AST05, AST08).**
   - `compile` відмовляє тілу, у якому є будь-що з цього:
     - приховані символи;
     - секрети;
     - токени шаблонів чату;
     - віддалені зображення;
     - raw HTML;
     - у skill: `` !`cmd` `` або блок ```` ```! ````.

     Фрази, схожі на інструкції моделі, і посилання на інші хости дають попередження.
   - Приховані символи в тексті frontmatter — помилка компіляції.
   - Сканер вдруге шукає фрази в згорнутій копії тексту: без прихованих символів, з fullwidth-літерами як звичайними. Base64 він декодує на глибину до двох шарів. Глибші або завеликі блоки отримують окрему позначку, а не вважаються чистими.
   - Налаштування вмикають `disableSkillShellExecution`: Claude Code не виконує shell зі skills і commands, хоч би звідки вони були. verify падає, якщо інший файл налаштувань це вимикає.
   - Нова перевірка `bodies` сканує кожен файл, що завантажується, разом з усіма файлами в теці skill. Файл, який не вдалося прочитати як текст, має статус `incomplete`, а не «чистий».
2. **4c. Конфігурація як код (AST02).**
   - Нова перевірка `project-config` падає в двох випадках:
     - спільні налаштування запускають команду, встановлюють plugins або перенаправляють трафік Claude;
     - будь-який файл налаштувань схвалює всі сервери `.mcp.json`.
   - Сервери з `.mcp.json` і такі самі ключі в локальному файлі дають попередження.
   - Налаштування задають `enableAllProjectMcpServers: false`.
3. **4d. Інвентар (AST06, AST07, AST09).**
   - `verify --json` перелічує всі agents, skills, rules і commands проєкту, користувача й увімкнених plugins: з відбитками, результатом сканування і часом перевірки.
   - Перевірка `inventory` падає, якщо особистий skill затінює проєктний (Claude Code віддає перевагу особистому).
   - Вона також попереджає про зовнішні skills, яких немає в `policy.external_skills`.
   - Агент може попередньо завантажувати лише skills, визначені в spec або перелічені в `policy.external_skills`; решта — помилка компіляції.
4. **4e. Журнал аудиту (AST09).**
   - Гейт записує кожен виклик інструмента до його виконання. Хук `audit-outcome` на PostToolUse і PostToolUseFailure записує, чим виклик закінчився.
   - Записи мають спільний `attempt_id`, обчислений з `session_id` і `tool_use_id`. Вони містять дайджести замість вмісту і відбиток spec.
   - Журнал лежить у `~/.mezha/audit`, за тією самою межею, що й approvals.
   - Виклик, який не вдалося записати, блокується.
5. **4f. Памʼять та інструкції (AST01, AST03).**
   - `memory.auto_memory = "read-only"` (так за замовчуванням) забороняє сесіям писати auto memory і транскрипти в `~/.claude/projects`.
   - Перед редагуванням будь-якого `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md` і `~/.claude/CLAUDE.md` Claude Code питає дозволу.
   - verify попереджає, якщо `autoMemoryDirectory` або `CLAUDE_CONFIG_DIR` переносить auto memory туди, де правило не діє.
6. **4g. Підписані коміти (AST02, AST07).**
   - `branch-protection` читає вимогу підписів окремим запитом із класичного правила, а також з активних rulesets.
   - Якщо захищена гілка приймає непідписані коміти, verify попереджає.
7. **4h. Маніфест дозволів (AST03).**
   - Агент без `tools` не компілюється.
   - `WebFetch`, `WebSearch` чи MCP-інструмент в `allowed_tools` skill дають попередження.

## Відхилені варіанти

- **Підписи ed25519 від видавців, Merkle root, transparency log, відкликання, репутація.** Це інфраструктура реєстру. Походження skill у проєкті дають git, захист гілки, CODEOWNERS і підписані коміти.
- **Поведінковий сканер на мовній моделі.** ADR-0006 уже відхилив LLM-суддю. Стандарт сам каже, що сканер не має бути єдиним барʼєром, тож сканування лишається детермінованим і advisory.
- **Підписи записів аудиту.**
  - Ключ лежав би на тій самій машині, тож проти її власника нічого б не дав. Проти агента журнал уже захищає межа на `~/.mezha`.
  - Hash-chain виявляє зміни посередині, але не обрізання й не перерахунок.
  - Для нього хуку довелося б чекати на блокування файла. Повільний диск міг би довести хук до timeout, після якого Claude Code пропускає виклик.
- **Окремий контейнер для кожного skill.** Skill — це prompt одного агента, а не процес. Команди й так виконуються в sandbox Claude Code.
- **Universal Skill Format.** Поки що це лише пропозиція. Документ відповідності показує, якими полями `mezha.toml` покрито поля USF. Експорт відкладено до portable skills (фаза 4).
- **Попередження на налаштування користувача в `project-config`.** `statusLine`, plugins і хуки в `~/.claude` — власні налаштування людини для всіх проєктів. Попередження на них стояло б майже в кожного, і сигнал загубився б. Тому з налаштувань користувача перевіряється лише схвалення всіх серверів `.mcp.json`.

## Наслідки

- Плюс: кожен захід стандарту має місце в коді або пояснення, чому його немає.
- Плюс: дві нові межі в самому Claude Code замість шаблонів: `disableSkillShellExecution` і заборона писати auto memory.
- Мінус: spec ламає сумісність. Агент без `tools` і попередньо завантажений неперелічений skill тепер дають помилку. Для pre-alpha це прийнятно; шаблон `init` і фікстури оновлено.
- Мінус: сесії більше не зберігають спогадів в auto memory самі. Хто цього хоче, ставить `auto_memory = "writable"`.
- Мінус: `verify` попереджає про кожен неперелічений особистий або plugin-skill, доки людина їх не перелічить.
- Мінус: журнал аудиту росте без обмежень, старі файли треба видаляти вручну.

## Крок 5: відкриті пункти

Після кроків 4a–4h у документі відповідності лишалося вісім відкритих пунктів і ще два рядки зі статусом «Open». Кроки 5a–5f закривають усі.

1. **5a. Сканер (AST08).**
   - Shell у блоках коду й inline-коді тіл читає той самий парсер, що й хуки. Лапки, порожні розгортання, змінні й підстановки більше не сховають завантаження чи декодування, передане в інтерпретатор.
   - Математичні й обведені літери стають звичайними. Кириличні й грецькі двійники згортаються лише в словах, що змішують їх з латиницею, і такі слова позначаються. Згортати весь текст не можна: український текст став би латиницею.
   - `tests/evasion.rs` проганяє опубліковані техніки обходу сканерів. Він показує, які з них сканер ловить, а які ні, і чому межа для других в іншому місці.
2. **5b. Відбитки зовнішніх skills (AST01, AST07).**
   - Запис у `policy.external_skills` може мати відбиток: `name@sha256:...`. Це SHA-256 усіх файлів теки skill, разом зі скриптами й ресурсами.
   - verify падає, коли такий skill змінюється.
   - Для запису без відбитка verify попереджає й друкує відбиток, який треба додати.
3. **5c. Skill eval (AST03, AST04, AST08).**
   - Кожен рядок записує відбиток виміряного `SKILL.md`, модель і версію Claude Code. verify попереджає, коли skill змінився після останнього eval.
   - Після завантаження skill кожен виклик інструмента звіряється з його `allowed_tools`, а розділ Manifest у звіті перелічує незадекларовані.
   - Це звіт, а не барʼєр: knowledge-skills законно ведуть агента до інструментів, яких самі не надають.
4. **5d. WebFetch (AST05).** `policy.fetch_allow` перелічує хости, до яких WebFetch може звертатися.
   - Без ключа WebFetch працює без обмежень, а compile попереджає. Так вирішив автор, щоб за замовчуванням не ламати роботу з документацією.
   - Зі списком гейт читає хост з URL так, як браузер, і блокує решту.
   - Редирект на інший хост — це новий виклик WebFetch, тож і ланцюжок посилань лишається в межах списку.
   - `[]` додатково вмикає `CLAUDE_CODE_DISABLE_WEB_FETCH`.
   - Посилання в тілах на хости поза списком — помилка компіляції.
   - Хеш вмісту не перевіряємо: WebFetch дає Claude переказ сторінки моделлю, а не її байти.
   - Правила deny разом з allow відхилено: у Claude Code allow не робить винятку з deny.
5. **5e. Звʼязки в журналі аудиту (AST09).**
   - Записи мають `prompt_id`.
   - Виклики субагента мають його `agent_id`, а результат виклику Agent — `spawned_agent_id`.
   - Посилання на батьківський виклик не може бути в записі допуску: Claude Code не передає його хукам до виклику. Звʼязок іде через запис результату.
6. **5f. Локальні інтерфейси (AST06).**
   - Broker ще не існує, тож вимогу записано в документації `mezha-broker`: автентифікувати кожного, хто звертається, і ніколи не довіряти адресі джерела.
   - Вже зараз `project-config` падає на сервері з `.mcp.json`, який працює на цій машині без автентифікації.

Наслідок: без `policy.fetch_allow` compile попереджає в кожному проєкті, доки людина не вирішить, куди WebFetch можна звертатися.

## Відкриті питання

Немає. Те, що лишилося, — межі підходу, а не відкладена робота. Їх перелічено в розділі «Known limits» документа відповідності.
